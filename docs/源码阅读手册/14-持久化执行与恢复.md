# 第 14 讲 持久化执行与恢复

把 run ID、运行状态与工具步骤对应到 SQLite 日志。

## 保存聊天记录与保存执行进度

会话历史能告诉你已经说了什么。假设程序在写文件后断电，要判断这个工具能否安全重试，还需要知道执行到了哪一步、结果是否已提交。这是持久化运行日志的用途。从 `_run_durable_once()` 看运行如何开始或接回，再读 `RunStore` 中运行、检查点和步骤的表。先看步骤的提交顺序，再看对话内容是怎样投影回会话存储的。持久化子任务另外涉及 `child_runs`、`child_containers` 和 `child_deliveries` 三张表，分别记录父子关联、容器和交付。

## 沿运行状态恢复

| 观察到的情况 | 接下来核对 |
| --- | --- |
| 运行已完成 | SDK 可以读回已提交结果，注意保护更新的会话历史 |
| 已暂停或中断 | 找到原会话、工作区和运行标识，检查最近保存的检查点 |
| 步骤结果不明 | 从外部系统核实是否已产生副作用，再记录确认过的结果 |
| 父运行正在等待子任务 | 从原步骤查子运行、容器与交付凭据，读第 19 章的沙箱路径 |

用 `list_runs()` 查看当前会话尚未结束的运行，再从 `list_run_steps()` 对照各步状态。需要人工处理时，先读恢复指南和相关测试，再使用 SDK 的决议接口。涉及文件修改、Bash 或外部服务时，判断依据来自真实执行结果和日志状态。

**思考与答案**　恢复是否等于从用户提示重新跑一次？持久化恢复以已提交检查点为起点，并复用已提交结果。对结果无法确认的副作用，先核实，不应盲目重跑。
