# 第 11 讲 上下文窗口压缩与卸载

理解历史变长时，到底有哪些数据进入模型。

## 请求窗口、历史压缩和大结果卸载

你已经聊了很多轮，现在又读了很大的日志。此时有三个问题：哪些旧消息能放进本次模型请求，是否需要用摘要缩短长期上下文，以及过大的工具输出如何保留供后续搜索。MiniBot 分别处理这三个问题。

| 机制 | 变化发生在哪里 |
| --- | --- |
| 请求裁剪 | 构造本次要发送的消息视图。无须在会话文件中删除旧轮次 |
| 上下文压缩 | 从已有历史生成摘要。读取和使用摘要应沿 Agent 与会话存储处理分支追踪 |
| 产物卸载 | 保存大工具输出的完整文本，模型先得到引用及可用预览，需要时再按范围或关键词读取 |

## 为什么总按整体轮次找边界

`prepare_model_request()` 会将前段裁剪候选对齐到用户消息，而用户补充给提问工具的答复仍属于原轮次。系统和开发者消息也可能被保留。在能够容纳最近一轮的前提下，构建器尽量找到较早的可用边界，为输出留出空间。最近轮次都放不下时会触发本地上下文错误。调试大日志场景时，先看该错误发生在请求前、模型响应后，还是工具结果被卸载的节点。

**思考与答案**　看到模型没有读到历史某段内容，能否据此判断原 JSONL 已被删除？不能。从本次模型请求无法推断磁盘历史，检查请求裁剪、压缩标记和存储代码各自的作用。
