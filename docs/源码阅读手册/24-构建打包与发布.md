# 第 24 讲 构建打包与发布

理解开发环境怎样生成可安装的 Python 包和静态 WebUI。

## 从源码树到可安装包

先看 `pyproject.toml`。`minibotclaw` 是发行包名，`minibot` 是 Python 导入名。`minibot` 和 `minibot-web` 则是安装生成的命令。理解这三个层次后，再看打包产物为什么同时需要 Python 模块和构建后的前端静态资源。仅有 Vite 源码，安装包启动后还需要相应的构建产物才能提供 WebUI。

## 静态资源为什么要先同步

Vite 在 `webui/dist/` 中生成页面和带哈希的文件。同步脚本把文件整理到 Python 包的静态资源目录，并校验旧哈希文件已经清理，确保页面引用与目录一致。打包后再运行归档检查脚本，确认 wheel 和 sdist 里包含需要的静态文件。两个检查发生在不同阶段，前者看构建目录与静态目录的对应，后者看最终归档。

## 阅读发布工作流

顺着 CI 读构建、同步、测试和打包。再读发布工作流，确认触发标签如何与项目版本匹配、PyPI 发布及 GitHub Release 分别在什么阶段发生。练习时可以本地构建归档并比较文件清单，阅读工作流就能核对发布过程。

**思考与答案**　为什么本地通过 Vite 开发服务器能打开页面，装好 wheel 却可能看不到？开发服务器直接提供前端内容。安装包的 WebUI 是否可用，要检查归档里是否确实包含同步后的静态资源。

## 使用与验证

本地可依次构建 WebUI、执行同步、生成 wheel 和 sdist，再运行归档检查。学习发布流程时读取工作流与 CI 记录即可。

```bash
cd webui
npm install
npm run build
cd ..
bash scripts/sync_webui_static.sh
uv run --with build python -m build
```

随后对本次构建的 wheel 和 sdist 运行 `scripts/verify_package_static.py`。使用 Bash 时可传入 `dist/*.whl dist/*.tar.gz`，使用 PowerShell 时可显式传入这两个归档路径。

在仓库根目录运行本讲的定向测试。测试可在未配置真实模型凭证的环境中执行。

```powershell
uv run --with pytest --with pytest-asyncio python -m pytest -q tests/test_server_ui_assets.py::test_resolve_static_dir_prefers_packaged_static_then_webui_dist
```
