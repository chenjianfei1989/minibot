# 第 09 讲 配置加载写回与系统提示词

从某个设置的值反查它从哪来、最后在哪使用。

## 配置生效之前经过哪些层

在仓库目录修改示例 YAML 后，启动程序发现模型没切换。第一步应检查程序实际读取的应用主目录。打开 `load_config()`，看它如何解析 `workdir`、`app_home` 与 `project_root`，并以应用主目录下的 `config/` 加载文件。仓库模板可参与首次生成，运行中的配置对象由解析结果和代码默认值组成。

`default.yaml` 同时可以出现普通值和环境变量占位符。例如 `${MODEL_ID:gpt-4.1-mini}`。在测试中对照进程环境与全局 `.env` 的输入，观察相应的解析结果。相对路径也有自己的基准，`skills_dir` 和 `hooks_dir` 都从配置目录解析，而会话路径要沿会话配置逻辑确认。不要只凭项目根目录猜测。

## 跟踪一次配置改动

挑一个真实改动，例如用 `/model config` 修改模型。先查 CLI 写回哪份文件，再看当前实例如何获得新配置。SDK 路径也值得对照：构造时可以传入预先构建的 `Config`，并选择工作目录、会话目录或持久化覆盖。最后看 `Agent.__init__()`，确认已解析的配置如何组装客户端、权限、工具与系统提示词。

**思考与答案**　如果示例 YAML 没有 `memory` 或 `session`，这两个模块就一定关闭了吗？要看解析器如何填充默认值。当前配置模型为两者提供了启用默认值，最终行为还需结合作用范围和工作区限制核对。

在 Windows 上，用户目录下的 `.minibot` 是默认的应用主目录。配置首次写入和各数据目录的来源见[附录 C](附录C-用户目录下的配置与运行数据.md)。

## 配置核对

对照 .env.example、config/default.yaml、config/hooks.yaml 和 config/mcp_servers.yaml。先验证进程环境与全局 .env 的关系，再逐项记录配置的来源、默认值、生效和写回范围。

## 使用与验证

在单独的临时应用主目录准备测试配置，把同一个模型变量分别放在 .env 和进程环境中，观察最后加载的值。

在仓库根目录运行本讲的定向测试。测试可在未配置真实模型凭证的环境中执行。

```powershell
uv run --with pytest --with pytest-asyncio python -m pytest -q tests/test_config_loading.py::test_load_config_env_precedence_process_over_global
```
