# 第 16 讲 追踪回归测试与模型评估

通过可观察记录解释执行过程，为调试选择合适的测试。

## 出问题时，先确定试图验证什么

一次模型回合答错了，未必意味着 Agent 循环坏了。先问：工具是否实际执行、执行失败后是否有下一次模型请求、模型是否理解了工具结果？运行追踪把这些问题映射到 `run_start`、工具调用及结束事件。沿 `RunTrace` 看怎样保存状态、耗时和关联标识，并核对允许写入的字段，避免把追踪当作包含完整聊天正文的日志。

## 两种验证各回答什么

脚本化模型回归测试控制模型逐步返回的内容，适合检验 MiniBot 本身会不会按预期分发工具、记录结果和恢复流程。真实模型评估用实际服务完成文件任务，可以衡量模型和工具接口组合后的任务表现。一次评估失败时，应先确定最后状态和工作区产物，再追到模型输出及工具用量。

做一个无真实凭证的对照：检查关闭追踪时工作区没有追踪文件，但 SDK 的正常正文仍返回。再阅读开启追踪的测试，用同一个运行 ID 串起动作。真实模型评估需有效模型配置，其结果应与模型、任务、预算一起记录。

**思考与答案**　脚本化模型测试通过，是否就能保证生产模型会选对工具？它证明程序在给定响应下按预期运行。实际模型是否会选对工具，需要使用包含真实响应的评估。

## 使用与验证

先跑不需要模型凭证的追踪测试，查看同一 run 的事件顺序。有意评估真实模型时再参照模型文件任务评估指南。

在仓库根目录运行本讲的定向测试。测试可在未配置真实模型凭证的环境中执行。

```powershell
uv run --with pytest --with pytest-asyncio python -m pytest -q tests/test_run_traces.py::test_disabled_has_no_files_and_chat_text_is_unchanged
```
