# 第 02 讲 模型请求组装

看到实际提交给模型的参数，并能解释兼容层。

## 从会话消息到服务商请求

上章得到的是 MiniBot 内部的消息列表。模型客户端还要准备服务商可读的请求。拿「请统计项目说明的行数」作例子，模型除了看用户消息，还需要知道系统规则、工具清单以及本次可生成的 token 上限。Agent 先通过 `prepare_model_request()` 估算请求体和可用空间，再把调整后的消息交给 `LLMClient`。第 11 章会细看历史很长时的取舍。

阅读 `LLMClient` 时把三个概念分开。客户端初始化配置决定连接哪个端点、用哪个模型和凭证。单次调用参数决定这次带哪些消息、工具和推理选项。返回对象则包含生成内容、结束原因和用量等信息，这些字段最终由 Agent 读取。用同一个会话切换生成方式时，变化发生在单次请求的 `stream` 和消费响应的方式上。

## 在请求边界检查数据

先在假客户端测试中找出捕获的关键字参数。对照请求构造处，判断 `messages` 里的系统提示词怎样放入，`tools` 什么时候随请求发出。随后沿同步和异步执行入口找调用服务商的位置。不同兼容端点对推理强度的支持不完全相同，客户端会转换特定服务商参数，并在能判定是不支持该参数时尝试省略重试。第 13 章讨论 Agent 层如何计算预算。

**思考与答案**　调整 `max_context_tokens` 能不能保证服务商一定接受请求？这个值用于 MiniBot 本地估算和裁剪。模型服务商仍可能按自己的分词和端点规则校验请求。
